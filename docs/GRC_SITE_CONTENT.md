# Bilingual website content and approvals

[README](../README.md) · [Developer introduction](introduction.md) · [Operations](GRC_OPERATIONS.md)

## Purpose and scope

Website content lets authorized GRC users edit English and Arabic copy across the public GRC site: landing page sections, existing cards, navigation, footer, contact page, FAQs, other information pages and the privacy and terms notices. The visual editor uses the same renderer and styling as the public website. Click text to open English and Arabic fields together. Use the page selector to work on other public pages. Add cards to the journey, information-page card groups, or custom sections. New sections are appended to the chosen page; existing landing sections and information-page sections can be removed and restored. Contact and legal forms remain protected, while custom sections can be added around them. Navigation destinations, imagery, dynamic dates, questionnaire content and application screens are not managed here. The default site remains visible until an approved revision is published. Privacy and terms previously saved in GRC Settings are copied to the new published store on first migration; subsequent legal text edits use this workflow.

## Configure access and approvals

A GRC App Admin opens **Website content** in the workspace. Under **Access and approval workflow**, select existing, active Frappe roles whose GRC users may edit. Selecting a role grants access to all signed-in GRC accounts holding it; the role must already be assigned to each user. Administrators always have editor and configuration access. The built-in platform Administrator remains a Desk account. Add one or more approval roles in the required order; each step requires a decision by a user who currently holds that role. At submission the workflow and submitter-approval setting are frozen. By default the submitter cannot approve or reject their own submission. An administrator may explicitly allow a submitter who holds the required role to decide. Changes to the configuration do not alter pending submissions.

## Draft, preview, review and publish

Click the text in the visual canvas, edit both languages in the dialog, and apply to the draft. Click a card or section to select it for structural controls. The **All text fields** panel remains available for bulk text edits. Use **Save draft** to persist text and structural changes. The shared draft uses optimistic concurrency: if another editor saved it first, reload before continuing. **Preview saved draft** opens a permission-checked, clearly marked preview; navigate between site pages without publishing. Save changes again before submitting. **Submit for approval** locks a snapshot, its live base, workflow and submitter. A reviewer opens the revision, previews the site, and approves or rejects the current step. Rejection requires a reason. Only the final approval atomically publishes the complete snapshot; until then the public endpoint returns only the previous live content. Site clients refresh published copy periodically.

A rejected or older revision can seed a new draft and approval cycle; discard an existing draft first. If another revision has changed the live site, stale drafts cannot be submitted and stale pending revisions cannot be approved. A reviewer may reject a stale pending revision, or an administrator may cancel a blocked submission with a reason; its audit record remains. Publication and audit events are stored transactionally. An administrator can view the full revision snapshots and paginated audit history, including the actor, timestamp, changed English and Arabic values, workflow configuration, submissions and decisions. Authorized editors and approvers can also see the history. These records are protected from ordinary portal document writes and deletes; trusted platform/database administrators retain their normal infrastructure privileges.

## Technical design and deployment

The static bilingual text catalogue lives in `grc/src/site-content-defaults.json`; `siteCopy` identifies each text pair with a stable key derived from the original English and Arabic strings. Preserve original keys when maintaining the source: changing a default pair changes its key and requires migrating existing published overrides. `scripts/check-site-copy.mjs` checks literal lookups. React renders text as text, not HTML. The `GRC Site Content` singleton holds current publication and role configuration; `GRC Site Revision` stores snapshots and `GRC Site Event` records actions. The `site_content_*` APIs enforce authorization, validate catalogue keys, serialize conflicting writes and publish only after the required decisions. The guest `public.site_content` endpoint returns approved copy only; revision previews require an authorized session.

Deploy on staging first: back up the site, deploy app files, run `bench --site SITE migrate`, run `bench build --app ia_maturity`, and restart backend services. The migration creates the content DocTypes and seeds legacy legal notices without changing the rest of the live copy. Verify public English and Arabic pages, role access, a preview, multi-step approval, a rejected revision and the audit trail before production rollout. Run `bench --site grc.local run-tests --module ia_maturity.grc.test_site_content --skip-test-records --skip-before-tests` only against an isolated test site, and run the Playwright site-content tests with the local preview.

Structural layouts and custom text are validated and stored in the same revision snapshot as the text catalogue. Every save and approval includes these changes; no layout change is published before final approval.
